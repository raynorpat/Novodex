# Phase 5: public box names and registry lifetime

The pinned oracle's public box vtable at RVA `0x106dc8` routes slots 29 and 30 to setters/getters at `0x233d0` and `0x24640`. The setter reaches the global `{internal shape*, name pointer}` registry through `0x8aea0 → 0xedc0`; the getter reaches its lookup through `0x95cb0 → 0xdf90`. Names are retained as pointers, without copying string bytes. Replacing an entry changes its name pointer; clearing the last entry frees the pair array and its 0x10-byte table header.

The staged actor target checks no name, first name, replacement, and clearing. Both oracle and candidate print `name_allocs=2.2`, `name_alloc_sizes=10.10`, and `name_free_sizes=10.10`. A descriptor name arrives through the same registry, with exact seven-allocation creation sequence `50.18.228.1c.10.10.260`. The named actor's immediate release frees only `18.260.1c.228.50`: the oracle does **not** remove its name-table entry during this release, so the candidate preserves that behavior. Twelve new registered lines raise the Phase 5 floor from 345 to 357.

Aimed replacement mutation kept the first name pointer. The oracle reported `actor box name_second=1.box-two`, the candidate `0.box-one`, and the staged differential failed with `stdout_delta=2`; restoring replacement returned it to zero. This drive does not cover growth beyond two names, stale-entry lookup after shape memory reuse, or SDK-level registry teardown. The existing `ShapeBase` analysis registry in `ObjectModel.cpp` is a separate scaffold and has not yet been unified with this runtime path.
