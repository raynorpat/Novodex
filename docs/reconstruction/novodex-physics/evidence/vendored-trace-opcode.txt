Vendored opcode: cdb execution trace of the Phase 4 differentials (vendored-correspondence Tasks 4 and 5a)
==========================================================================================================

Generated by tools/vendored_trace.py (`script`, `parse`, `identity`, `report`) for
vendored-correspondence Task 4 and re-run for Task 5a. It is the execution evidence behind the
`hits`, `outcome` and `family_best` columns of
evidence/phase4-third-party-map/vendored_coverage.csv.

WHICH BINARY, AND WHY IT IS THE SHIPPED CODE. The Phase 4 differentials are oracle
differentials: each loads the pinned oracle and calls its rows at their RVAs, and the
candidate side of every comparison is the vendored code linked into the test exe itself,
not a staged NxPhysics.dll. So the exe is what executes candidate code, and the exe is what
is traced. It links the same NxQhull.lib and NxOpcode.lib that NxPhysics.dll links with
/WHOLEARCHIVE (CMakeLists.txt; External/CMakeLists.txt compiles them once, with one set of
flags), so the objects are the same. `vendored_trace.py identity` checks the linked result
too: every traced group's body in the exe is compared with its body in the candidate DLL,
instruction by instruction, with relocated operands and branch/call targets compared as the
symbol (plus offset) each resolves to in that image's own linker map. All traced bodies are
the same code but one: AABBTreeBuilder's scalar deleting destructor, whose COMDAT the exe's
linker took from the harness's own object (compiled with the harness's flags) -- that group
has no x87 code. Where an exe body came from another object with identical code, the
per-group line says so.

METHOD. cdb x86 runs the exe to exit with one breakpoint per distinct exe address of a
MATCH/SHAPE/REVIEW/DIFF group (functions the exe's /OPT:REF dropped or inlined have no
address and are marked `-`). Each breakpoint increments a counter in a page the script
allocates at 0x60000000 and, at the cap, disables itself. At every family boundary (the
harness's nxReport entry, which carries the family name) the script prints `SEG <family>`,
dumps the counters and clears and re-arms them; a `layout` boundary at nxDriveQhullPure
closes the candidate-only layout assertions, and (Task 5a) a `release` boundary at
nxDriveSap closes the harness's release of the Task 4 models, which no family compares. The exe has no PDB, so addresses are taken from
the exe's own linker map (/MAP, added for this purpose) relative to $exentry.

CLASSES (Task 5a). Each family is classified from its own harness line: `exact` (no word
differs), `lastbit` (divergent, no discrete word differs, same length, every differing float
or double within 4 ulp), `discrete` (anything else). An execution is a segment with hits plus
the hit-less sibling segments reported right after it (the families the same drive filled),
and its class is the worst of those families; `vendored_trace.py coverage` gives each group
its best execution. The `families and classes` line below lists each family's class.
